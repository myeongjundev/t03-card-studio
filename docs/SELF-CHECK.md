# 자체 점검 자료

**모든 측정은 공개 주소 https://myeongjundev.github.io/t03-card-studio/ 에서 수행했습니다.**
로컬 개발 서버가 아니라 배포본입니다.

측정 방법은 화면을 눈으로 보는 대신 **캔버스 픽셀을 직접 읽는 것**입니다.
글자 색과 같은 픽셀만 골라 개수와 무게중심(중심 좌표)을 재면,
"바뀐 것 같다"가 아니라 "얼마나 어디로 바뀌었다"를 숫자로 말할 수 있습니다.

## 1. 이미지 불러오기

파일 입력에 File 객체를 실어 보내 실제 `pickImage` 처리 경로를 그대로 통과시켰습니다.
운영체제 파일 선택 대화상자만 건너뛰었고, 형식 검사·로딩·렌더링은 모두 실제 코드입니다.

| 검사 자료 | 화면에 표시된 메시지 | 캔버스 결과 |
|---|---|---|
| **PNG** 세로 800×1400 | 이미지를 불러왔습니다. (800 × 1400px) | 배경색 픽셀 0.0% — 이미지가 화면을 가득 채움 |
| **JPEG** 가로 1200×450 | 이미지를 불러왔습니다. (1200 × 450px) | 배경색 픽셀 0.0% — 이미지가 화면을 가득 채움 |
| **투명 PNG** 600×600 | 이미지를 불러왔습니다. (600 × 600px) | 배경색 픽셀 40.9% — 투명 영역으로 배경이 비쳐 보임 |
| **GIF** (지원하지 않는 형식) | 지원하지 않는 파일 형식입니다(image/gif). PNG 또는 JPEG 파일을 선택해 주세요. 지금까지의 편집 내용은 그대로 있습니다. | **직전 이미지가 그대로 유지됨** |

투명 PNG 에서 배경색이 40.9% 보이는 것이 정상입니다.
원 바깥이 완전 투명이라 그 아래 배경색이 그대로 드러납니다.

## 2. 문구 조작이 즉시 반영되는지

문구 `측정`, 기준 상태는 가로 50% · 세로 50% · 140px · 흰색입니다.

| 바꾼 값 | 글자 픽셀 수 | 글자 중심 좌표 | 해석 |
|---|---|---|---|
| (기준) | 13,328 | (544, 523) | 캔버스 중앙 |
| 가로 위치 50% → **20%** | 13,328 | (**220**, 523) | 가로만 324px 이동, 세로 그대로 |
| 세로 위치 50% → **80%** | 13,328 | (544, **847**) | 세로만 324px 이동, 가로 그대로 |
| 크기 140 → **280px** | **53,271** | (551, 506) | 픽셀 수 4.0배 — 크기 2배의 면적비와 일치 |
| 색상 흰색 → **#ff5577** | 13,226 | (544, 522) | 새 색으로 거의 같은 픽셀 수가 검출됨 |

크기를 2배로 올렸을 때 픽셀 수가 정확히 4배 가까이(13,328 → 53,271, 3.997배) 나오는 것이
글자가 실제로 2배로 커졌다는 근거입니다.

색상 변경 시 픽셀 수가 13,328 → 13,226 으로 미세하게 줄어든 것은
글자 가장자리 안티에일리어싱 픽셀이 색마다 조금씩 다르게 섞이기 때문이며, 정상입니다.

모두 **적용 버튼 없이** 값을 바꾸는 즉시 반영됐습니다.

## 3. 세 화면비

| 비율 | 내부 해상도 | 글자 픽셀 수 | 글자 중심 |
|---|---|---|---|
| 1:1 | 1080 × 1080 | 13,328 | (544, 523) |
| 4:5 | 1080 × 1350 | 13,347 | (544, 658) |
| 9:16 | 1080 × 1920 | 13,347 | (544, 943) |

세로 위치 50% 설정이 각 비율의 높이에 맞춰 따라갑니다.
글자 크기(픽셀 수)는 비율이 바뀌어도 유지됩니다 — 캔버스 폭이 항상 1080px 로 고정돼 있기 때문입니다.

## 4. 미리보기와 다운로드 일치

미리보기 캔버스의 픽셀을 읽어 두고, 내려받는 것과 같은 PNG blob 을 만들어
다시 디코드한 뒤 서로 대조했습니다.

| 상태 | 파일 크기 | 다른 서브픽셀 |
|---|---|---|
| 9:16, 일반 문구 | 63,850 byte | **0** |
| 9:16, 자동 축소가 적용된 상태 | 52,154 byte | **0** |

1080×1920 캔버스의 서브픽셀은 8,294,400개입니다. 그중 **0개**가 다릅니다.

두 결과를 맞춰 놓은 것이 아니라, 미리보기 캔버스를 그대로 파일로 만들기 때문입니다.
다시 그리지 않으므로 어긋날 여지가 구조적으로 없습니다.

수정 후 같은 입력에서 넘침 0 · 잘림 0 이 되었으며, 축소된 크기를 화면에 알립니다.

## 6. 템플릿 관리

배포본에서 실제로 조작한 결과입니다.

| 검사 | 결과 |
|---|---|
| 생성 | `배포확인 A`, `배포확인 B` 2개 저장 확인 |
| 삭제 | A 삭제 후 저장 데이터에 `배포확인 B` 만 남음 |
| 새로고침 유지 | 새로고침 후에도 `배포확인 B` 유지 |

개발 중 로컬에서 수행한 상세 검사:

| 검사 | 결과 |
|---|---|
| 템플릿 3개 생성 | 서로 다른 비율(1:1 / 4:5 / 9:16), id 모두 고유 |
| 불러오기 | 비율·문구·색상·배경 전부 복원, 캔버스 해상도 재설정 |
| **수정** | 개수 3→3 유지, **id 와 생성시각 보존**, 수정시각만 갱신, 다른 템플릿 무변경 |
| 삭제 | 확인창 후 저장 데이터에서 제거, 새로고침해도 되살아나지 않음 |
| 저장소 손상 | 앱 정상 동작, 원본을 `.corrupt-<시각>` 키로 보존 |

수정을 따로 확인한 이유는, 수정 버튼이 새 템플릿을 추가하는 방식으로 동작하는 것이
과제에서 금지한 가짜 기능이기 때문입니다. 개수와 id 가 함께 유지되는 것까지 확인했습니다.

### 템플릿에 저장하는 항목

`id` · `name` · `createdAt` · `updatedAt` · `ratio` · `fit` · `bgColor` · `transparentBg`
· `text` · `textX` · `textY` · `fontSize` · `color` · `lineHeight` · `align`

배경 이미지는 저장하지 않습니다. 브라우저 저장 공간이 보통 5MB 남짓이라
1080×1920 이미지를 담으면 템플릿 두세 개로 가득 차기 때문입니다.
이 사실은 템플릿 화면에도 적어 두었습니다.

## 7. JSON 가져오기 / 내보내기

### 정상 파일 왕복

내보낸 파일로 저장소를 복원한 결과, 아래 12개 항목이 **전부 일치**했습니다.

`name` `ratio` `fit` `bgColor` `transparentBg` `text` `textX` `textY` `fontSize` `color` `lineHeight` `align`

내보낸 파일에서 개인정보·토큰 패턴은 검출되지 않았습니다.

### 잘못된 파일 (5종)

매번 **기존 템플릿이 그대로 유지**됐습니다.

| 입력 | 화면에 표시된 메시지 |
|---|---|
| 문법 깨짐 | JSON 문법이 올바르지 않아 가져오기를 중단했습니다. (Expected ',' or '}' … position 26) 기존 템플릿은 그대로 있습니다. |
| 필수 항목 누락 | **2번째** 템플릿에 `ratio` 항목이 없습니다. 가져오기를 중단했으며, 기존 템플릿은 변경되지 않았습니다. |
| 타입 오류 | 1번째 템플릿의 `fontSize` 은(는) 숫자여야 합니다. … |
| 값 범위 초과 | 1번째 템플릿의 `textX` 값 5 이(가) 허용 범위(0 ~ 1)를 벗어났습니다. … |
| 지원하지 않는 비율 | `3:2` 은(는) 지원하지 않습니다. 1:1 / 4:5 / 9:16 중 하나여야 합니다. … |

몇 번째 항목의 어떤 필드가 왜 잘못됐는지까지 알려 줍니다.
검증 함수는 저장소에 접근조차 하지 않는 순수 함수라, 검증 도중에 기존 데이터가
바뀔 수 있는 경로 자체가 없습니다.
