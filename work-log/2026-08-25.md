## 1. History 경계 결함 — 테스트를 쓰다 발견

전날 로그에는 "History boundary 테스트 추가"만 적혀 있었는데,
테스트를 쓰려고 코드를 읽다가 **실제 결함**을 찾았다.

### 증상

모습(Persona)을 고른 뒤 **0.6초 안에** 문구를 옮기면,
되돌리기 한 번에 문구 이동과 모습 변경이 **함께** 사라진다.

### 원인

`usePreset`/`useEra`가 `lastChangeAtRef.current = 0`으로 묶음을 끊었다.
이건 **앞쪽만** 끊는다. 직후 effect가 `lastChangeAtRef.current = now`로
덮어쓰므로, 0.6초 안의 다음 편집은 모습 단계에 흡수된다.

### 해결

시각 하나 대신 묶음 상태를 들고 다닌다.

```js
{ lastChangeAt, isolated }
```

`isolateBurst`로 표시된 변경은 자기 뒤에 시각을 남기지 않는다(`lastChangeAt: 0`).
그래서 앞뒤 어느 편집과도 묶이지 않는다.

판단 로직은 `history.js`의 순수 함수 `advanceBurst`에 뒀다. React 없이 테스트된다.

### 브라우저 확인 (단위 테스트만으로는 배선을 증명하지 못한다)

| | 결과 |
|---|---|
| 모습 → 시대 → 문구, 185ms 안에 연속 실행 | 3단계로 기록 |
| 되돌리기 3회 | 문구 → 시대 → 모습 순으로 하나씩 복원 |
| **수정 전 코드로 되돌려 같은 절차 재현** | 되돌리기 1회에 문구 + 시대가 **함께** 사라짐 |

마지막 줄이 중요하다. 고친 코드가 통과하는 것만으로는 결함이 있었다는 증거가 안 된다.

## 2. `persona: null` / `era: null` 비대칭 해소

- `era: null` → 거부 (`raw.era !== undefined` 검사)
- `persona: null` → **통과** (`raw.persona ?? base.persona`가 null을 기본값으로 흡수)

`?? `는 "필드가 없음"과 "null이 적혀 있음"을 구분하지 못한다.
era와 같은 규칙으로 맞췄다 — **없으면 기본값, 값이 있으면 반드시 검사.**

legacy 이관(`professional`/`chaotic` → `normal`)은 그대로 유지.

## 3. 접근성 — 실제 결함이었다

전날 로그에는 "Persona 그룹에 `aria-label` 추가"라고 적혀 있었는데,
확인해 보니 `aria-label`은 **이미 있었다.** 없는 건 `role="group"`이었다.

```jsx
<div className="preset-grid" aria-label="온라인에서 보여줄 모습">
```

role 없는 `div`의 `aria-label`은 스크린리더가 읽지 않는다. 그동안 무의미했다.
Era 그룹(`.era-timeline`)에는 `role="group"`이 제대로 있었다.

## 10. CI 에 테스트 추가 (처리 완료)

배포 워크플로가 `npm ci` → `npm run build` 만 해서, 테스트 56개가 배포
경로에서 한 번도 실행되지 않았다. `npm test` 를 `build` **앞에** 넣었다.
실패하면 job 이 거기서 멈춰 `upload-pages-artifact` 까지 가지 않는다.

### 초록불이 거짓말을 할 수 있었다

스텝을 넣고 초록불을 확인했지만, 그것만으로는 **테스트가 실제로 돌았는지
알 수 없었다.** 로그는 admin 권한이 없어 못 읽는다.

그래서 직접 확인해 봤다 — 테스트 파일이 하나도 없는 프로젝트를 만들어
`node --test` 를 돌리니 **exit 0**. "전부 통과" 와 "아무것도 실행 안 함" 이
똑같이 초록불로 보인다. 파일이 옮겨지거나 이름 규칙이 바뀌면 조용히 그렇게
될 수 있다.

통과 개수를 읽어 0 이면 실패시키도록 가드를 넣었다.

```
passed=$(awk '/ pass [0-9]+$/ { p = $NF } END { print p + 0 }' ...)
[ "$passed" -lt 1 ] && exit 1
```

로컬에서 양쪽 다 확인: 이 저장소 `통과한 테스트: 56` → exit 0,
테스트 없는 저장소 `통과한 테스트: 0` → exit 1.

**이제 초록불은 "테스트가 실제로 돌았고 전부 통과했다" 를 뜻한다.**
로그를 못 읽어도 그 사실이 보장된다 — 확인 방식이 구조로 바뀌었다.

커밋: `c72e2cd`, `3b1d22a`. 배포 재실행 성공.

### 시대별 렌더 회귀

그 구조가 무너지지 않는지 4가지로 고정했다 — 상태 필드, `renderCard` 소스,

**빈 테스트가 아닌지 확인함**: 가이드를 캔버스에 그리도록 고치니

## 12. 헤드리스 브라우저로 CI 에서도 픽셀 검사

12장에서 "픽셀은 브라우저에서, 구조는 CI 에서" 로 나눴던 것을 합쳤다.
playwright 를 devDependency 로 넣고 배포 워크플로에서 실제 Chromium 을 띄운다.

### 왜 골든 이미지를 안 쓰는가

PNG 바이트는 OS·폰트·그래픽 스택에 따라 달라진다. 내 Windows 에서 만든
기준 이미지는 CI 리눅스에서 **절대** 맞지 않는다. 그런 테스트는 회귀를 잡는
대신 매번 실패해서 결국 꺼진다.

대신 **같은 실행 안에서 반드시 성립해야 하는 관계**를 검사한다. 두 결과를
그 자리에서 만들어 비교하므로 환경이 달라도 흔들리지 않는다.

| 검사 | 내용 |
|---|---|
| 미리보기 = 내보내기 | 3개 조합, 다른 바이트 **0** |
| 안전 영역 | 가이드 켬/끔 PNG 해시 동일 |
| 시대 구분 | 18개 조합 결과 픽셀 전부 다름 |
| 투명 배경 | 세 시대 모두 알파 보존 |
| 오류 | 페이지·콘솔 오류 0건 |

### e2e 가 단위 테스트와 겹치지 않는다는 것도 확인했다

처음 뮤테이션을 잘못 짰다. 9:16 이면 **항상** 띠를 그리게 했더니 켬/끔이
똑같아서 테스트가 통과했다. 테스트가 약한 게 아니라 내 뮤테이션이 그 결함을
재현하지 못한 것이었다.

실제 결함 시나리오 — 안전 영역 토글이 캔버스에 직접 덧그리는 것 — 으로
다시 하니 e2e 가 잡았다. **그리고 단위 테스트는 전부 통과했다.**
`renderCard` 는 멀쩡하기 때문이다. e2e 가 새 영역을 덮고 있다는 증거다.

### 307초 → 13초

처음엔 픽셀 배열을 브라우저 밖으로 넘겨서 비교했다. 1080×1920 이면
800만 개가 넘어 직렬화에만 수십 초가 걸렸다(첫 테스트 하나가 224초).
비교를 브라우저 안에서 끝내고 **숫자만** 받도록 바꿔 13초가 됐다.

### 단위 테스트 글롭을 명시한 이유

`node --test` 는 `test/` 아래 **모든** 파일을 테스트로 취급한다.

- 헬퍼 2개가 테스트로 세어지고 있었다 (66 → 실제 64)
- 이대로 뒀으면 CI 가 브라우저 없이 e2e 를 실행하려 했을 것이다

`node --test test/*.test.js` 로 명시해 둘 다 막았다.

### CI 소요

| 단계 | 시간 |
|---|---|
| 단위 테스트 | 1s |
| build | 0s |
| Chromium 설치 | 26s → **12s** (캐시 적중 확인) |
| 픽셀 e2e | 12~13s |

브라우저 캐시 키에 playwright 버전을 넣었다. 버전을 올린 뒤 옛 브라우저
캐시를 복원하면 설치가 깨지기 때문이다.

커밋: `5223b24`, `37aa91f`.

## 13. 배포본 눈으로 확인 — 결함 3개 발견

지금까지는 숫자로만 검증했다. 실제 화면을 **눈으로** 보려고 playwright 로
배포본 스크린샷을 찍었다(이 환경은 브라우저 창이 표시되지 않아 MCP
스크린샷이 안 된다. 어제 겪은 제약을 playwright 로 우회했다).

**그리고 바로 결함이 나왔다.** 픽셀 e2e 는 전부 통과하는 상태였다.
"미리보기 = 내보내기", "시대가 서로 다름" 같은 관계는 지켰지만
**결과물이 보기 좋은지는 아무도 검사하지 않고 있었다.**

### 결함 1 — 기본+2012 는 글자가 거의 안 보인다 (앱 자신이 불합격 판정)

앱 내장 가독성 검사가 직접 말하고 있다.

```
배경와의 대비 1.1:1 — 기준 3:1 에 못 미칩니다
```

원인: `normal:2012` 조합은 밝은 레이아웃 기준으로 잡혀 있다
(`bgColor #eef1f4`, `color #172033`, `strokeWidth 0`).
그런데 시대 재설계로 2012 가 **검은 필름 베이스**가 되면서, 어두운 글자가
어두운 필름 위에 놓였다. **조합 스타일이 시대 재설계를 따라가지 못했다.**

9개 조합 대비 측정 결과 이 조합만 불합격이다.

| | 2004 | 2012 | 2026 |
|---|---|---|---|
| 기본 | 16.5:1 | **1.1:1 불합격** | 18.9:1 |
| 소셜 | 16.1:1 | 16.1:1 | 18.4:1 |
| 친한 친구 | 11.2:1 | 21.0:1 | 17.6:1 |

### 결함 2 — 2012 필름인데 날짜 각인이 `'04`

`renderCard.js:155` 에 `"'04 8 24"` 가 하드코딩되어 있다.
2012 시대 카드에 2004 년 날짜가 찍힌다. 필름 감성의 핵심 장치가
시대를 틀리게 말하고 있다.

### 결함 3 — 조합 4개가 손보지 않은 채로 남아 있다

`COMBINATION_STYLES` 에 정의된 것은 5개뿐이다.

- 정의됨: `close-friends:2004`, `normal:2012`, `normal:2026`,
  `social:2026`, `close-friends:2026`
- **미정의**: `normal:2004`, `social:2004`, `social:2012`, `close-friends:2012`

미정의 조합은 Persona 기본 스타일로 대체되는데, 그 스타일은 시대 장식을
고려하지 않은 값이다. 기본+2004 는 흰 글자에 굵은 검은 테두리가
**흰 미니홈피 카드** 위에 얹혀 속이 빈 글자처럼 보인다. 대비 검사는
테두리 기준으로 16.5:1 이라 통과시키지만, 보기에는 의도한 결과가 아니다.

### 관찰 — 데스크톱 레이아웃 불균형

왼쪽 편집 패널이 약 2,000px 인데 가운데·오른쪽은 1,140px 에서 끝난다.
오른쪽 아래가 크게 비고, 기본 조작을 하려면 스크롤을 많이 해야 한다.

### 잘 나온 것

2012 필름은 스프로킷 홀·`COLOR 400`·비네팅·주황 날짜 각인이 어우러져
의도한 감성이 분명히 읽힌다(날짜 값만 틀렸다).
모바일 375px 에서 가로 스크롤 없음, 페이지·콘솔 오류 0건.

## 14. 필름을 프레임에서 화질로 바꿈

사용자가 바로잡아 준 것: 원한 것은 **필름 카메라로 찍어 인화된 사진의
화질**이지, 필름 스트립의 생김새가 아니었다.

내가 그리고 있던 것(검은 베이스, 좌우 스프로킷 홀, `COLOR 400` / `12A →`)은
필름 **통**의 모습이다. 필름으로 찍은 **사진**의 모습이 아니다.

### 바꾼 것

프레임 장식을 전부 걷어냈다. 이미지가 화면 전체를 쓰고, 그 위에 실제
인화물에서 오는 네 가지를 겹친다.

| 겹치는 것 | 방법 |
|---|---|
| 색바램 | 크림색을 낮은 알파로 덮어 검정을 들어 올린다 |
| 따뜻한 색조 | 주황색을 `soft-light` 로 — 밝기는 두고 색만 물들인다 |
| 비네팅 | 방사형 그라데이션 |
| 입자 | 고정 씨앗 난수 128×128 타일을 `overlay` 로 반복 |

`composition.js` 에서 2012 의 imageBox 를 지웠다. 인화된 사진은 프레임 안의
작은 그림이 아니라 그 자체가 화면 전체다.

### 입자를 타일로 만든 이유

픽셀마다 난수를 뿌리면 1080×1920 에서 200만 번이다. 편집할 때마다 버벅인다.
타일을 한 번만 만들어 패턴으로 반복하면 렌더당 `createPattern` + `fillRect`
한 번이다.

### 씨앗을 고정한 이유는 성능이 아니다

`Math.random` 을 쓰면 같은 설정인데도 매번 다른 그림이 나온다. 그러면
**"미리보기와 저장본이 같다" 를 검사할 수 없다.** 저장한 템플릿을 다시
불러와도 다른 카드가 된다.

e2e 로 고정했다 — 시대를 옮겼다 돌아온 뒤 PNG 해시가 같은지 본다.
**빈 테스트가 아닌지 확인함**: `Math.random` 으로 바꾸고 타일 캐시를 끄니
실제로 실패했다.

### 곁들여 풀린 것

- **날짜 각인 연도** — `'04` 하드코딩을 시대에서 가져오도록. 2012 카드에
  2004년이 찍히고 있었다
- **기본+2012 가독성 결함** — 대비 1.1:1 → **9.6:1**. 원인이 검은 필름
  베이스였으므로 걷어내면서 함께 풀렸다. 이제 9개 조합 전부 기준을 넘는다

| | 2004 | 2012 | 2026 |
|---|---|---|---|
| 기본 | 16.5:1 | 1.1 → **9.6:1** | 18.9:1 |
| 소셜 | 16.1:1 | 16.1:1 | 18.4:1 |
| 친한 친구 | 11.2:1 | 21.0:1 | 17.6:1 |

- 회귀 스냅샷이 `globalCompositeOperation` 변화도 잡도록 보강

### 배포본 확인

사진을 올리고 2012 ↔ 2026 을 오갔다. 같은 사진이 2012 에서는 입자가 끼고
색이 바래고 가장자리가 어두워지며 오른쪽 아래에 `'12 8 24` 가 찍힌다.
2026 은 원본 그대로다. 차이가 분명히 읽힌다.

커밋: `09b0a65`.

## 15. 2004 = 미니홈피 틀 + 피처폰 사진 화질

사용자 아이디어. SKT 수업이라는 맥락에서 나왔다 — 옛날 피처폰으로 찍은
사진처럼 만들면 어떨까.

**미니홈피 틀은 그대로 두고 그 안의 사진만 바꿨다.** 2004년에 미니홈피
사진첩에 올라가던 사진이 실제로 카메라폰 사진이었기 때문이다. 틀과 화질이
함께 있어야 그 시절이 된다. (필름처럼 틀을 걷어낼 수도 있었지만, 여기서는
틀 자체가 그 시절의 일부다.)

| 만드는 것 | 방법 |
|---|---|
| 화소 뭉침 | 180px 버퍼로 줄였다가 `imageSmoothingEnabled = false` 로 되돌린다 |
| 색 띠 | 채널당 10단계 양자화 |
| 저조도 노이즈 | 어두운 픽셀일수록 크게. 밝은 곳은 깨끗하다 |
| 초록 기울기 | 화이트밸런스가 늘 초록으로 기울어 있었다 |

### 보간을 끄는 것이 핵심이다

`imageSmoothingEnabled` 를 켜 두면 화소가 부드럽게 뭉개져서 "저화질" 이
아니라 그냥 "흐린 사진" 이 된다. 꺼야 화소가 네모로 보인다.

### 노이즈 세기를 두 번 조정했다

처음 값(진폭 92, 6단계)으로 렌더해 보니 **피사체가 사라지고 모래폭풍만
남았다.** 피처폰 사진도 무엇을 찍었는지는 알아볼 수 있어야 한다.
진폭 26, 10단계로 낮췄다.

숫자만 봤으면 "필터가 잘 적용됨" 으로 넘어갔을 것이다. 렌더해서 눈으로
본 덕에 잡았다. 13장에서 배운 것이 그대로 또 나왔다.

### 성능

무거운 픽셀 연산을 **작게 줄인 버퍼에서만** 한다. 1080×1080 원본에 직접
하면 100만 번이 넘지만 180px 버퍼는 2만 번이 안 된다. 어차피 결과가
저화질이라 원본 해상도로 계산할 이유도 없다.

문구를 연속으로 고치며 잰 렌더 시간: 중앙값 **16.8ms**, 최대 18.1ms.

### e2e 로 고정

- 사진을 올린 뒤 2004 의 **색 가짓수가 2026 의 절반 미만**이어야 한다
- 다시 그려도 같은 결과여야 한다(고정 씨앗 난수)

**빈 테스트가 아닌지 확인함**: 필터를 끄니 `10240 → 9001 로 충분히 줄지
않음` 으로 실패했다.

### 배포본 확인

같은 사진을 세 시대로 찍었다. 2004 는 화소가 굵게 뭉치고 하늘에 띠가 지며
초록으로 기울고, 2012 는 입자가 끼고 색이 바래며 날짜가 찍히고, 2026 은
원본 그대로다. 세 장이 분명히 다르고 전부 피사체를 알아볼 수 있다.

커밋: `749bc8a`.

## 16. 레퍼런스를 받고 2004 를 다시 만듦

사용자가 참고 이미지를 보내 줬다. 두 가지가 어긋나 있었다.

### 화질 — 각진 화소가 아니었다

내가 만든 것은 굵은 네모 화소 + 색 띠 + 초록 기울기였다. 레퍼런스는
전혀 달랐다.

| 레퍼런스의 특징 | 내가 만든 것 |
|---|---|
| 부드럽게 뭉개진 저해상도 | 각진 네모 화소 |
| 보라·라벤더 기울기 | 초록 기울기 |
| 하이라이트가 날아감 | 대비 유지 |
| 둥근 모서리 검은 테두리 | 없음 |

고친 방법:

- 버퍼 180px → **300px**, 되돌릴 때 보간을 **켠 채로** 둔다.
  끄면 레트로 게임처럼 보인다
- 색 양자화를 버리고 **대비 0.70 배 + 검정 살짝 들어올림**
- 밝은 픽셀일수록 흰색·분홍으로 밀어 올린다(하이라이트 블룸)
- 빨강·파랑을 올리고 초록을 내린 뒤, 위에 `screen` 으로 보라를 얹어
  그림자를 들뜨게 한다
- **둥근 모서리 검은 테두리** — 레퍼런스에서 가장 알아보기 쉬운 표시

### 세기를 세 번 조정했다

1. 1차: 하이라이트가 통째로 날아가 피사체가 사라졌다
2. 2차: 되돌렸더니 아무 일도 안 일어난 것처럼 보였다
3. 3차: 대비 0.70 / 블룸 문턱 152 / `screen` 0.15 에서 맞았다

매번 렌더해서 눈으로 봤다. 숫자만으로는 판단할 수 없는 종류다.

### 틀 — 싸이월드로

"미니홈피" 라고만 하고 일반적인 파스텔 카드를 그리고 있었다.
싸이월드에서 눈에 남는 것을 골라 넣었다.

- 왼쪽 **링 바인더** — 미니홈피를 한 장의 그림으로 떠올릴 때 가장 먼저 나오는 것
- `TODAY 23 | TOTAL 12,458` — **TODAY 숫자는 빨강, TOTAL 숫자는 남색**.
  이 색 대비가 상단의 인상이었다
- `Director. My Life` + 파란 `EDIT` 칩
- `TODAY IS... ♥ 그냥` 기분 바
- 사진첩 칸, 하단 BGM

화면을 통째로 옮기지는 않았다. 그러면 카드가 아니라 스크린샷이 된다.

### 경로 합성에서 막힌 곳

둥근 테두리는 바깥 사각형에서 안쪽 둥근 사각형을 빼서(even-odd) 만든다.
그런데 `roundedRect` 가 안에서 `beginPath` 를 불러 **바깥 사각형을 지워
버렸다.** 결과는 테두리가 아니라 사진 전체가 까맣게 칠해진 것이었다.

경로만 덧그리는 `roundedRectPath` 를 따로 뒀다.

### 미정의 조합 문제가 함께 풀렸다

2004 조합 셋을 모두 정의했다. 전에는 `normal:2004`, `social:2004` 가
미정의라 Persona 기본 스타일로 대체되어 흰 페이지 위에 흰 글자 + 검은
테두리가 얹혔다(속이 빈 글자처럼 보였다).

셋 다 같은 자리를 쓴다 — 기분 바 아래, BGM 줄 위. 색만 다르다.
흰 페이지 위에 얹히므로 **외곽선은 쓰지 않는다.**

| 조합 | 글자색 | 대비 |
|---|---|---|
| 기본+2004 | 진회색 | 8.9:1 |
| 소셜+2004 | 분홍 | 5.7:1 |
| 친한 친구+2004 | 파랑 | 5.3:1 |

### e2e 기준을 설계에 맞게 바꿨다

기존 검사는 "색 가짓수가 절반 미만" 이었다. 부드럽게 뭉개는 방식으로
바꾸니 **보간이 중간색을 만들어 오히려 늘었다**(10,240 → 36,451).
테스트가 실패해서 알았다.

색 가짓수는 더 이상 맞는 잣대가 아니다. 실제 의도를 재도록 바꿨다.

- 사진 한가운데의 **밝기 표준편차**가 낮아지는가 (대비 저하)
- **파랑 − 초록** 평균이 커지는가 (보라 기울기)

가운데만 재는 이유는 2004 는 사진첩 칸 안에, 2026 은 화면 전체에 사진이
들어가서다. 가운데는 두 경우 모두 사진이다.

**빈 테스트가 아닌지 확인함**: 필터를 끄니 `대비가 충분히 낮아지지
않았다: 2026 10.5 → 2004 14.1` 로 실패했다.

### 작업 중 실수

문서 수정 스크립트를 `node -e` 안에 넣었는데, 셸이 백틱과 `|` 를 해석해
스크립트가 망가진 채 커밋이 나갔다. 코드는 맞고 문서만 옛 내용이었다.
파일로 옮겨 다시 적용했다(`25b01c7`).

**긴 스크립트는 `node -e` 대신 파일로 쓴다.**

커밋: `6dd8b78`, `25b01c7`.
